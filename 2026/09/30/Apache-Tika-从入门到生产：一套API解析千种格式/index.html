Apache Tika 从入门到生产：一套 API 解析 PDF/Word/Excel/PPT/图片上千种格式（含 Spring Boot 封装与 OCR）

做企业开发的同学，大概率都碰到过这类需求：

  • 做知识库 / RAG 系统：要把用户上传的 PDF、Word、PPT、甚至扫描件全部扒成纯文本，切块丢向量库；
  • 做全文检索：文件服务器上几十万份文档，要统一建索引，能按关键词搜到内容；
  • 做内容审核 / 合规审计：员工上传的附件里有没有敏感词？合同里有没有不合规条款？
  • 做元数据归档：一份合同的作者是谁、哪天创建的、最后谁改的、多少页？

这类需求的共同点是：格式杂、数量大、写解析代码非常痛苦——

  • 写 Word 用 POI，.doc 和 .docx 还不是一套 API；
  • 写 PDF 用 PDFBox，加密 PDF 还得绕一圈；
  • 写 Excel 又得换 Fesod/POI；碰到 HTML、RTF、压缩包、图片 OCR？
  • 每多一种格式，就得多学一套库、多写一套分支，维护起来就是噩梦。

今天的主角 Apache Tika 就是来解决这个痛点的。它把上千种文件格式的解析能力封装成一套统一的 API，你不用管底层是 POI 还是 PDFBox，丢文件进去 → 出来就是 文本内容 + 元数据 + MIME 类型。

配合上一篇 Spring Boot + Apache Fesod 生产级 Excel 组件，你的项目就能形成完整的 “Excel 精细化读写 + 全格式文档内容解析” 闭环。

0）Apache Tika 是什么 & 为什么选它

0.1 一句话定位

Apache Tika 是 Apache 基金会旗下的开源内容分析工具包，能够自动检测上千种文件格式，并从中统一提取文本内容、元数据、语言类型。

你可以把 Tika 理解成文档解析界的 Facade 模式——底层仍然使用 POI、PDFBox、HtmlParser、Tesseract 这些成熟解析器，但上层给你一套 10 分钟就能上手的统一门面。

0.2 Tika 能解析什么？（1000+ 格式部分代表）

类别支持的格式
办公文档Word（.doc/.docx）、Excel（.xls/.xlsx，配合 Fesod/POI）、PowerPoint（.ppt/.pptx）、Visio、Outlook MSG、OpenDocument（ODT/ODS/ODP）、RTF
PDF标准 PDF、加密 PDF（需密码）、带表单 PDF、PDF/A 归档版
网页与标记HTML、XHTML、XML、JSON、YAML、Markdown
纯文本.txt / .log / .csv（含自动编码识别）
压缩包ZIP / TAR / GZIP / RAR / 7z（可递归解包提取内容）
邮件.eml / .mbox / Outlook PST
图像 & OCRJPEG / PNG / TIFF / BMP（能取 EXIF；配合 Tesseract 可 OCR 图片文字）
多媒体元数据MP3 / FLAC（ID3 标签）、MP4 / MOV（音视频元信息）

0.3 核心三大能力

能力说明
🔍 MIME 自动检测不看后缀名，根据文件二进制 Magic Number + 内容特征判断真实类型，防改后缀名绕过
📝 内容提取输出纯文本（也可输出 XHTML 结构化结果，保留标题、表格层次）
🏷️ 元数据提取作者、标题、创建/修改时间、页数、分辨率、EXIF、Creator Tool 等几十种属性

额外可选能力：🌏 语言检测（中英文混排自动识别）、🖼️ OCR（Tesseract 集成）、🔗 递归解析（ZIP 里的 Word 直接扒出来）。

0.4 和”挨个用解析器”对比

维度手写”if PDF, if Word, if Excel”Apache Tika
支持格式加一种格式加一套代码，维护爆炸一套 API 通吃 1000+
MIME 检测fileName.endsWith(".pdf") → 改后缀立刻翻车Magic Number + 内容特征，真实类型 99%+ 准确
学习成本POI、PDFBox、jsoup 每一套都要查文档3 个核心类 + 2 个方法，10 分钟上手
升级兼容每个解析器自己升版本，依赖冲突家常便饭Tika 团队已经帮你把依赖对齐、避过坑了
企业 RAG/知识库场景一个月搭不完 + 后续持续踩坑引入依赖 → 写几十行 Service → 上线 🚀

一句话结论：只要你的系统需要解析 2 种以上的文档格式，Tika 就是 ROI 最高的选择。

8）生产环境避坑清单 ⚠️（踩一次调 3 天）

坑现象解决方案
BodyContentHandler 默认截断 10w 字符长文档后半段内容丢失一定用 new BodyContentHandler(-1)，不要用默认构造器
Tika 实例反复 new性能差、GC 频繁、解析器重复初始化全局单例 Bean，Tika 是线程安全的
POI / PDFBox 版本冲突NoSuchMethodError / ClassNotFoundException引入 tika-parsers-standard-package 的 pom，把自己项目里老的 poi-ooxml / pdfbox 升到 Tika 对齐的版本，或直接 exclusions 排除
超大文件 OOM200MB+ PDF 解析到内存爆炸1) 用 TikaInputStream 包装 File（不走 byte[]）；2) 设置 BodyContentHandler 字符上限；3) 超过阈值的文件单独丢 Tika Server 集群处理
加密 PDF 直接抛异常EncryptedDocumentException先 metadata.set(PDFParser.PASSWORD, pwd) 再 parse；也可以在 catch 里友好提示”请先解密”
Excel 解析”丢数据”公式、图表、批注没出来Tika 对 Excel 是”全量文本抓取”，不负责公式计算和格式；精细化业务还是用 Fesod
中文 OCR 全问号/乱码扫描件出来一堆 ???1) 没装 chi_sim 语言包；2) setLanguage("chi_sim+eng")
Zip 炸弹 / 超大压缩包recursive 解析时解压出几十 GB 塞满磁盘配置 ZipParser 的 maxExtractSize、maxMemoryBytes，或干脆禁用递归解压
Tika Server 连接超时大文件 / OCR 跑几十秒客户端把 readTimeout 调到 60s~300s；服务端 -Xmx 至少 2g

9.2 和 Fesod 的分工配合（划重点）

很多同学纠结：Tika 能解析 Excel，那还要 Fesod 吗？ 答案是 两者都要，分工不同：

维度Apache TikaApache Fesod
定位全格式内容索引（1000+ 种格式一把梭）Excel 精细化读写（只专注电子表格）
Excel 输出纯文本拼接、不带公式结果按行按列、批注、合并单元格、样式全保留
写 Excel❌ 不支持✅ 链式 API + 模板填充 + 多 Sheet
大文件批量导入导出❌ 不适合（没有分批入库监听器）✅ 流式读 + 分批写 + 错误报告
适用场景知识库、全文搜索、合规审计、RAG 文档解析业务系统的”用户导入/报表导出”

配合起来就是：

  1. 用户上传一份 Excel → Fesod 做精细化导入（校验字段、分批入库、错误报告）；
  2. 同时丢给 Tika 做全文索引（用户在搜索框输入关键词，能搜到这份 Excel 里的内容）。
